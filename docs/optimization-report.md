> **⚠ 缺陷 35 更正（2026-09-19 深夜）—— 收尾流水线的返回值契约错误（P0，"静默瘫痪"）**
>
> `scripts/hurink_finalize.py` 的 `merge()` 返回 `(rows, dup)` 二元组，而 `steps` 表的
> 约定是返回 rc（int）。第一版直接写 `lambda: merge(...)`，于是 `rc` 恒为非空元组、
> **真值恒为真**：这条流水线**每一次运行都会在第 0 步"失败"退出**，并把整个 `rows`
> （实测 **7.5 MB**）当成"错误信息"打印出来。合并本身其实一直是好的。
>
> 危害不在于它崩，而在于它**同时制造"假成功"与"假失败"**：退出码是 1，但"失败原因"
> 是一屏数据、看起来像日志；真正的原因（第 1–4 步一步都没跑）反而没有线索。
>
> **现场**：主实验跑完（66/66、5940 行、0 重复键）后，后台守护 `_wait_finalize.py`
> 并未产出 `hurink_aig.json`。手动跑 `--dry-run` 才让这条 7.5 MB 的"错误"现形。
> 根因是**契约不统一**——函数说"我返回数据"，调度器说"你返回 rc"，两处各自都对，接口错了。
>
> 已加 `merge_step()` 适配器（仅在有重复键时返回非零）＋ 3 条回归锁（含突变检验：
> 还原成缺陷版后 2 条测试立即失败）。顺带修掉同一函数里**跨盘符 `os.path.relpath`
> 抛 `ValueError`** 的脆弱点（一行显示代码足以崩掉整条流水线）。
>
> **另一条实验台观察**：后台守护进程在 13:16 被回收（日志戛然而止），而主实验继续跑到
> 13:16 之后很久。**长时后台守护本身也需要被守护** —— 这次的损失为零，纯属侥幸：
> 因为收尾逻辑被写成**幂等、可随时手动重跑**的显式阶段，而非"只有自动化会做"。
> 分工应保持：**自动化负责省事，显式阶段负责兜底**。

## 1. 工程优化：热路径

### 1.1 方法：先用真实计时，别信 cProfile

第一版改造直接照着 cProfile 的输出做（`scripts/profile_hotspots.py`），
把 `_repair_ma_for_os` 里"逐工序挑候选机器"改成 numpy 批量化
（`argsort` + fancy-index + 位掩码）。结果 **反而慢了 8–11%**。

原因：cProfile 会给**每一次 Python 函数调用**插桩，而纯 Python 循环里函数调用极密，
于是它把"C 实现的小函数"的相对成本严重高估；按这个排序去"消灭函数调用"，
消灭掉的其实是最便宜的那部分。

**改用真实墙钟计时器**（`scripts/profile_wall.py`：`Timer` 类包住模块，只在**函数边界**
插桩，用"父扣子"分别给出**含子调用的总耗时**与**函数体自身的耗时**两列），
方向立刻对了。只保留两列里的一列是不够的 —— 看"总耗时"会高估上层函数，
看"自身"会漏掉真正被反复调用的叶子。

```
# logs/_pw_new.txt（优化后，G=60）表头
函数                                          总耗时s       自身s      调用数       占比%    us/call
```

### 1.2 七项改动（全部保持随机流逐位不变）

```
init_random : 随机工序序 + 随机机器
init_ls     : 随机工序序 + t2 最小机器
init_gw     : 随机工序序 + 负载最轻机器
                          ↑
              OS（工序顺序）这一维**三条分支都没用**
```

`OS` 是 FJSP 编码里和机器选择并列的另一个自由度，而 MIX3 只在 MA 维度做文章。
所以候选改进就一句话：**用派工规则直接生成 OS**。

### 2.2 变体定义（`core/operators.py: INIT_VARIANTS`）

配比记作 `(random, ls, gw, os_spt, os_mwr)`：

| 臂名 | 配比 | 含义 |
|---|---|---|
| `I_rand` | (1,0,0,0,0) | 纯随机 = 论文 RMOEA/D1 |
| `I_mix3` | (1,1,1,0,0) | **论文口径 MIX3**（其余臂的配对基准） |
| `I_half_r` | (2,1,1,0,0) | 一半随机 + 各 1/4 |
| `I_no_r` | (0,1,1,0,0) | 无随机分支 |
| `I_gw_spt` | (1,1,1,1,0) | 四分支各 1/4（含 OS-SPT） |
| `I_spt` | (1,1,0,1,0) | 用 **OS-SPT** 替换 GW 分支 |
| `I_mwr` | (1,1,0,0,1) | 用 **OS-MWR** 替换 GW 分支 |

两条新派工规则（`init_os_spt` / `init_os_mwr`）：

- **OS-SPT**：每步从"各工件待排的下一道工序"里挑 `t2` 最短的入列；
- **OS-MWR**：每步挑"剩余工序 `t2` 之和"最大的工件入列（先把长工件清掉，
  避免它们在序列尾部堆成 makespan 瓶颈）。

两者都以 `explore=0.25` 的概率改选随机工件（否则同一 run 内 1/3 个体会完全同质），
且**无条件调用一次 `rng.rand()`**，使随机流消耗稳定、可复现。

**等价性锁**：`init_variant="mix3"` 与论文口径 `init_mix3` 在 3 实例 × 7 种
`n_pop`（含 99/101 这类不整除值）上**逐位相同**。

### 2.5 机制：为什么"只在 Mk10 上"成立不是偶然

把初始化里的搜索成分剥掉，直接测**派工规则本身的质量**（`explore=0`，
`MA` 一律取 `t2` 最小机器，30 次算术平均的 makespan）：

| 实例 | 规模（工件×机器 / 总工序） | 随机 OS | **MWR** | SPT | MWR/随机 | SPT/随机 |
|---|---|---|---|---|---|---|
| Mk05 | 15×4 / 106 | 288.1 | 235.8 | 436.5 | 0.818 | 1.515 |
| **Mk07** | 20×5 / 100 | 354.3 | 236.8 | 300.0 | **0.668** | 0.847 |
| **Mk09** | 20×10 / 240 | 704.0 | 558.8 | 1541.5 | **0.794** | 2.190 |
| **Mk10** | 20×15 / 240 | 606.2 | 366.8 | 1168.8 | **0.605** | 1.928 |

MWR 在**所有**实例上都是好规则（makespan 降到随机的 0.61–0.82 倍），Mk10 上最强。
那为什么只有 Mk10 的最终 HV 受益？因为**初始优势要能"守到终点"才有用**，而这取决于
该实例上初始化的**总杠杆**有多大 —— 同一批实测里：

| 实例 | `I_rand` 相对 `I_mix3` 的差距（= 初始化总杠杆）盒口径 | **实例边界口径** |
|---|---|---|
| Mk10 | −25.69% | **−7.36%** |
| Mk09 | −13.78% | **−6.17%** |
| Mk07 | −11.70% | **−1.58%** |

> **⚠ 缺陷 26：这条机制解释在正确口径下不成立，必须改写。**
> 盒口径下三实例是"2.2× 落差（Mk10 ≫ Mk09 ≈ Mk07）"，看起来正好解释 Mk10 独好；
> 实例边界口径下是 **Mk10 −7.36% ≳ Mk09 −6.17% ≫ Mk07 −1.58%** ——
> **Mk09 的杠杆与 Mk10 同级，净增量却是 0**。所以"杠杆大 → 收益大"**解释不了 Mk09**，
> 只在"Mk07 杠杆最小 → 收益也最小"这一端成立。

**正确的机制解释（本轮，见 `docs/new-arch-report.md` §4.4）**：真正与净增量单调的是
**`I_mwr` 相对 `I_mix3` 的 makespan 杠杆**（ρ=**+0.952**，置换校正 p=**0.0006**，n=10）——
三个正增益实例恰好就是该杠杆 > 2% 的三个（Mk06 +7.96、Mk10 +6.57、Mk08 +2.83），
其余 7 个的 |杠杆| ≤ 0.52%。**"初始优势要能守到终点"这句话本身没错，
错的是拿"random vs MIX3"的杠杆当代理** —— 该用"MWR vs MIX3"的杠杆。

- 初始化的总杠杆随实例变化（**Mk10 ≳ Mk09 ≫ Mk07**），
  但**杠杆不是净增益的充分条件**（Mk09 是反例）；
- 在"MIX3 已经比 MWR 强很多"的实例上（|杠杆| 大），200 代内搜索把差距补平 → 净效应 ≈ 0。

**顺带一个反例**：`I_spt` 与 `I_mwr` 结构完全相同，只换了派工规则，
在 Mk09/Mk10 上 SPT 的 makespan 是随机的 1.9–2.2 倍（**主动变差**），
所以 `I_spt` 表现 ≈ `I_mix3`（n.s.）—— 上表里"派工规则质量"与"最终 HV"是一致的。

### 2.6 其余边界

1. **没有对 `explore` 做扫参**（固定 0.25）。`explore` 是"派工 vs 随机"的混合比，
   理论上还有空间，但**这轮不测、不声称**。
2. `I_mwr` 的 `MA` 选择用的是 `t2` 最小机器（与 `init_ls` 同规则），
   而原先被替换掉的 GW 分支提供的是**负载均衡型机器多样性**。
   所以 `I_mwr` 与 `I_mix3` 的差异不止 OS 一处 —— 但 §2.3 的 `I_spt`
   对照把"是否只是去掉了 GW"这一解释排除掉了（`I_spt` 同样去掉了 GW，却没有增益）。
3. **默认值未改**。论文口径仍是 `init_variant="mix3"`，新变体是显式开关，
   理由是复现论文的表 5/表 6 必须保持口径不变（见 `docs/paper-vs-reproduction.md`）。
4. 留出集两实例规模不同（Mk07 20×5、Mk09 20×10），但**结论方向相同**（都塌到 +0.3%），
   所以"只在 Mk10 上成立"不能用"实例难度"一句话糊过去 —— 它是**杠杆分布**的问题。

## 5. 对论文 / 下一轮的含义

1. **本轮没有产出"新算法变体"**，产出的是两条可复核的事实：
   - **工程**：这把实验台快了 1.5×，且**数值逐位不变** —— 可以直接用于把
     `G 200 → 586` 那类"预算扫参"实验的成本压下来（见 `MEMORY.md` §7）。
   - **算法**：初始化中的 `OS` 维度（论文 MIX3 从未使用）**在 Mk10 上能换来 +8.6%~+10.5%**，
     但在 Mk07/Mk09 上 ≈0。这是一个**有边界的**结论，不是普适改进。
2. **论文里可以怎么写**（诚实版）：
   - 不能写"+8.64% 的方法改进"。要么写**边界条件**——"初始化的收益高度依赖实例
     （Mk10 初始化总杠杆 −25.7%，Mk09/Mk07 仅 −13.8%/−11.7%），因此本文方法与
     初始化策略的交互是后续工作"；要么**补实例**（把 OS-MWR 跑到 Mk01–Mk10 全部 10 个实例上，
     看是否存在"杠杆大 → 收益大"的单调关系）。后者才是能让这条结果站住的路。
   - 若要继续，"初始化杠杆"这个量（`I_rand` 与 `I_mix3` 的差）本身就是一个
     **可先验计算的实例特征候选**，比"RL 选择"那套更有希望。
3. **仍然成立的两条老结论**（见项目 `MEMORY.md` §7）：这个基准远未饱和
   （`G 200→586` = +11.1%，且所有 RL 组件效应 ≤±2%），以及"等算力对照"是必须的。

   > **⚠ 2026-09-18 更正（缺陷 22，见 `docs/new-arch-report.md` §1/§3）：**
   > 「远未饱和」这半句**已被推翻**。`G 200→586 = +11.1%` 是 **HV 盒口径**产物；
   > 实例边界口径下令同一比较只有 **+0.77%**。而 G=2000（10× 算力）实测显示
   > 末段 250 代的 HV 增量仅为首段的 **0.1%–3.3%** → **G=200 已高度饱和**。
   > 另一半（"所有 RL 组件效应 ≤±2%"）**成立且被加强**：终点口径下
   > Q-PAS 与 RL 选算子都是 **0/10 显著**（p=0.908 / p=0.805）。
   > 「等算力对照是必须的」这条也成立，但**必须用求值次数（FE）而非墙钟**
   > —— 本实验台的并行墙钟已被证明不可用于臂间比较（同报告 §5）。
4. **本轮新增的三条方法论教训**（都值钱）：
   - 定位性能热点**不要用 cProfile**：它会给每次函数调用插桩，严重高估纯 Python
     循环里小函数的相对成本 —— 按它做批量化改造实测**变慢 8–11%**。
     用真实墙钟计时（`profile_wall.py`）才拿到正确方向（−35%）。
   - **跨实例共享 HV 归一化盒会造出假结论**：同一份数据在合并盒下 HV 能从 0.0038 摆到 1.0402。
     凡是要跨实例汇总量，**先按实例分组**（见 §3 缺陷 14、15）。
   - **盒里的臂集必须等于"参与比较的臂"**，多一个都不行 —— 无关臂会把盒撑大，
     于是 rel% / dz 全部偏移，而且**偏移量随臂离盒边界的远近而不同**
     （`I_rand` 偏 3.4pp，`I_mwr` 只偏 0.04pp）。所以：凡引用"相对差"，
     必须同时写明归一化盒的**臂集**与**口径**（见 §3 缺陷 18、`MEMORY.md` §1）。

## 8. 复核结论

**可以带走的**：

1. **工程优化 −35%（1.5×）成立**，且验得比首轮更严（4 配置 × 3 实例、整字段零差异）。
   这是纯工程收益，可以直接用来压低 `G 200 → 586` 那类预算扫参的成本。
2. ~~**`OS-MWR` 的"Mk10 特有 +8.64%"成立**，留出集"判负"也成立 —— 两条都经得起独立复算。~~
   **⚠ 前半条已被推翻（缺陷 26）**：补到 n=10 后 **Mk06 / Mk08（均未调参）也显著为正**
   （+0.73% / +0.54%，≈29/30），故正确表述是"**只在能赚的实例上赚**"，不是"Mk10 特有"；
   且 `+8.64%` 是**盒口径**，实例边界口径为 **+0.690%**。
   "留出集判负"（Mk07/Mk09 均 n.s.）仍成立。
   **数据本身两条都经得起独立复算 —— 被改的是解释，不是数字。**
3. **盒的臂集口径已修死**，并加了回归锁；此后凡引用相对差，必须同时写臂集。

**必须带走的警告**：

> 这一轮的两个 P0 缺陷（14 / 18）都是**同一个物理错误的两种表现**：
> **HV 是相对的，盒一变，数值就变。**
> 而且偏移不是全局常数 —— 离盒边界越远的点，被扭曲得越厉害
> （`I_rand` 偏 3.4pp，`I_mwr` 只偏 0.04pp）。
> 所以"结论方向没变"这句话**不能**用来给旧数字开脱：
> 方向没变只是运气好（这里是因为效应量太大）。
> 一次"复算对不上"就足以让整份报告的数字全部作废 —— 而这次是自查出来的。

**复核本身也产出了东西**（不是走过场）：8 项检查里 **4 项没通过**
（效应量、图表数字、文档命令、以及盒子口径），共查出并修掉 **2 个新缺陷（18 / 19）**
外加绘图脚本里同一缺陷的第二份拷贝。这说明：

> 首轮"134 passed + 6 张图 + 报告数字自洽"是**看起来绿**的；
> 真正让它变可靠的是**换一条路径重算一遍**。
> 对交付物来说，"我跑通了"和"它是对的"之间，隔着的就是这一步。
